# 收尾与清理（用户说"收尾""清理"或要汇总时才做）

这一份是编排者流程主干（`~/.drover/pkg/flow/dispatch.md`）第 9 节"任务收尾"拆出来的，走到这一步时读：主会话转来用户的"收尾"、"清理 <任务>"、"出一份汇总"时；你是子编排者、收到上层发的"收尾"时。

用户说"收尾"时，第一步先写收尾汇总，再清理，最后在 rollup 写"完成"。用户说了"收尾"（或"清理"）就是同意删 `drover cleanup` 核实通过的 worktree 和分支（主干第 7 节），核实不过的照旧问。条目 worktree、集成 worktree 和试集成 worktree 都要清。

- **只要汇总、不说清理**（"出一份汇总""把变更和配置列一下"）：只做第 1 步，状态文件记一行 wrapup.md 的路径，再按第 8 步写 rollup，不清理。rollup 结论的第一条写"汇总完成，未清理"，"清理"一条列出待清理的 worktree 和分支。主会话看到未清理，不关你的 tab。
- **只说清理、不说收尾**（"清理 <任务>""把 worktree 清一下"）：只做第 2–5 步，不写汇总；rollup 写清理结果（删了什么、留了什么和原因），"收尾："那一行不变（收尾过、写着"留 …"的，清完了改回 `收尾：先别，已经收尾过了`，还留着的改成现在留的）。
- **清理被拒绝**（cleanup 的 `kept` / `remove_failed`：还有没推送的改动或提交、agent 在干活、`worktree remove` 被拒，或者用户不同意删某条分支）：汇总照写，"提交"一节的"没推送的"把它们列出来，"清理"一节写保留了什么、为什么。要用户定的写进 rollup 的"需要你决定"，状态标"等你决定"；用户定了再接着清理，补完"清理"一节再写"完成"。用户定了先留着（或者没让删）的，第 8 步写"留 …"那种。

原因：收尾时除了清理，还要汇总变更、提交、配置。先汇总再清理，是因为清理前 worktree、分支、集成记录都还在，核对远端的结果能直接写进汇总；汇总也是收尾的交付物，清理没做成也要有。

1. **收尾汇总**：写 `~/.drover/<slug>/wrapup.md`，一个任务一份，留档。
   - 先生成带事实的骨架：

     ```bash
     ~/.drover/bin/drover wrapup --slug <slug> --draft ~/.drover/<slug>/wrapup.md
     ```

     `wrapup` 只收集事实，不改仓库和任务记录：每个仓库每条目标分支的推送记录和远端是否还包含推送的提交、推送范围里的迁移 / 配置 / 部署 / 依赖文件和新增的环境变量 / 配置键引用（线索，不是结论）、整体检查的结果、待清理的 worktree 和本地分支，子编排者的推送记录一起带上（收集规则见 docs/reference.md 的 wrapup）。已有 wrapup.md 时拒绝覆盖，确认要覆盖再加 `--force`；远端头本地没有时提示加 `--fetch`（只 fetch 那条分支）再核对；`--no-remote` 跳过远端核对。没有推送记录的任务会给出提醒，"提交"一节按状态文件手写。
   - 再把所有 `（待填）` 换成实际内容：变更总结、数据库执行情况、配置说明、上线事项、未决等，来源是状态文件、worker 报告、迁移执行记录、用户的决定。没有的写"无"并加半句理由，**不留 `（待填）`**。骨架里的线索（推送范围里碰到的配置文件、新增的环境变量 / 配置键引用）逐条核对，确认不用改的写进"不需要改配置的"。
   - 格式（骨架按它生成）：

     ```markdown
     # 收尾汇总：<slug>

     目标：<状态文件开头的目标>
     编排者：<名>；涉及仓库：<仓库1>, <仓库2>
     收尾：<MM-DD HH:MM>

     ## 变更总结
     - <功能 / 修复点，一条一句，用户看得懂的话>
     - <仓库>：<主要文件或模块>（共 N 个文件）

     ## 提交
     | 仓库 | 分支 | 提交 | 范围 | 远端核对 |
     |---|---|---|---|---|
     | <仓库> | <目标分支> | <短 sha> | <a..b>（N 个提交） | <仍在 origin/<分支>（远端头 <短 sha>）/ 不在 / 未核对：原因> |
     - 没推送的：<条目分支或本地提交及原因>；全部推了写"无"

     ## 数据库
     | 仓库 | 迁移 | 测试环境 | 生产 | 核对 |
     |---|---|---|---|---|
     - 没有就写"无"，加半句理由（比如"只用已有字段"）

     ## 配置
     | 位置 | 配置项 | 值 / 动作 | 环境 | 状态 |
     |---|---|---|---|---|
     | <服务（Nacos / .env / 环境变量 / nginx）> | <键> | <新增 / 修改 / 核对 / 可删：值或怎么填> | <测试环境、生产> | <已改 / 待改> |
     - 不需要改配置的：<一两句，说明为什么不用改>

     ## 上线
     - 顺序：<哪个仓库先上；配置在哪一步之前 / 之后改；没有要求写"无，随常规发布">
     - 上线前：<…；没有写"无">
     - 上线后：<验证、回填、通知…；没有写"无">

     ## 验证
     - 整体检查：<一行，取 accept-integrate 的结果>
     - 没做的：<浏览器实测、线上验证…；都做了写"无">

     ## 未决
     - <每条一两句说清是什么、为什么做、不做会怎样，同 rollup 的写法；没有写"无">

     ## 清理
     - 已删：<worktree、分支、pane、workspace>
     - 保留：<…和原因；没有写"无">
     ```

   - 骨架的"清理"一节先列出待清理的 worktree 和分支，第 7 步再改成实际结果。
2. **清理，先看结论**：`~/.drover/bin/drover cleanup --slug <slug> --dry-run`。它逐个 worktree 和没有 worktree 的同类本地分支核实：没有进行中的 merge / rebase / cherry-pick；里面的 agent 不在 working / blocked；已提交的和没提交的改动都在这个任务推过的某条远端分支（的历史）里。条目提交在集成时解冲突改写过、原文在远端对不上的，按集成记录认（`integrate` 记着它摘成了哪个提交，那个提交在远端分支里就算交付）；没提交的改动一律按内容核实。核实规则（逐文件找、三方合并、集成记录怎么认、哪些情况算不在远端）见 docs/reference.md 的 cleanup，核实不了的一律不删。核对的远端分支来自推送记录（`refs` 写明每条的来源），先 fetch 到最新，fetch 不了的不拿来核对。推送没落盘的老任务（推送记录里没有这条分支）加 `--target <远端>/<分支>` 补上核对分支（可重复；传错了内容对不上，就是不删）。结论：`would_remove` / `kept`（`reasons` 写哪个文件、哪个提交不在远端，哪个 agent 在干活）；`uncommitted_found_in` / `found_in` 写明每个文件在哪个提交上对上的；`integrated` 列按集成记录核实的提交，`rewritten` 列这些提交改过的文件里和远端对不上原样的（集成时改写过，或者解冲突时没带上），`patches` 是删之前会存下这些提交原始版本的 patch 路径。
3. **去掉 `--dry-run` 再跑一次**：核实通过的删 worktree（workspace 开着用 `herdr worktree remove --workspace <id>`，会关掉 workspace 和里面的 agent；workspace 没开直接 `git worktree remove`），再 `git branch -D` 本地分支；没有 worktree 的同类本地分支核实后也删。带 `integrated` 的先把那些条目提交的原始版本存成 patch（`~/.drover/<slug>/integrated-<分支>-<时间>.commits.patch`，存成了才删）。核实不过的永远不删、不手工删。`kept` 的原因写进汇总，照上面"清理被拒绝"问用户；`remove_failed` 带着 herdr / git 的报错，先查原因再问。主检出永远不动。
4. 状态文件里记了 `source_workspace_opened`，并且那个 workspace 里没有 agent 时，`herdr workspace close <ID>`。必须先完成第 3 步：worktree 的 workspace 挂在它下面。
5. 把 cleanup 的结果记进状态文件：删了哪些 worktree / 分支、关了哪些 agent（`agents`）、留了哪些和原因；按集成记录核实的（`integrated`）记下存的 patch 路径（`patches`）。
6. 状态文件追加收尾记录：写一行 wrapup.md 的路径，不把全文抄进状态文件。
7. 补上 wrapup.md 的"清理"一节：实际删了什么（worktree、分支、pane、workspace），保留了什么和原因；按集成记录核实后删的，写上 patch 路径和 `rewritten` 列的文件。
8. rollup 状态标"完成"，"收尾："改成 `收尾：先别，已经收尾过了`（看板收尾那一格显示"已收尾"、不能再点）；收尾做完但留了东西（上面"清理被拒绝"：用户定先留着，或者 cleanup 核实不过、用户没让删）写 `收尾：先别，已经收尾过了，留 <留了什么，简短，如"1 个 worktree">`（看板显示"已收尾，留 …"、不能再点），以后用户说"清理 <任务>"清完了改回 `收尾：先别，已经收尾过了`；只写了汇总、没清理的写 `收尾：可以`，用户再说收尾时接着清理。"结论"写精简版（下面的格式，整份 rollup 照旧不超过 40 行）。主会话原样转给用户，然后关掉你所在的 tab；用户要看全文自己打开 wrapup.md，或者来问你。（写"留 …"的原因：留了东西如果只写"可以"，看板显示能点的 [收尾]，再点只会让 cleanup 再跑一遍、照样留下。）

   ```
   目标：<…>

   - 收尾完成。汇总全文：~/.drover/<slug>/wrapup.md
   - 改了什么：<1–3 行>
   - 提交：<仓库> <分支> <短 sha>（每个仓库每条分支一行）
   - 验证：整体检查 <存档路径>：<结果>，覆盖推上去的 <短 sha>（没覆盖的写明差了哪些提交）
   - 数据库：<无（理由）/ 每项一行：仓库 迁移 测试环境 生产>
   - 配置：<无（理由）/ 每项一行：位置 配置项 动作 环境 已改/待改>
   - 上线：<顺序和前后要做的，1–3 行；没有写"无，随常规发布">
   - 未决：<…；没有写"无">
   - 清理：已删 <N 个 worktree、M 个分支、K 个 pane>；保留 <…>
   ```
